# DeepAgent Starter vs JiuwenSwarm 上下文工程:对比、实践与排查

# 第一部分:两个项目对比

## 一句话总结

**Starter 是"一个处理器干所有事",JiuwenSwarm 是"五个处理器各干各的"。**

Starter 优点是简单、严, 缺点是粗、脆。JiuwenSwarm 优点是细、能扛长会话, 缺点是配置项多到吓人。

## 一、处理器数量

- **Starter**:1 个 `HermesStyleCompactProcessor`,所有逻辑塞在 `compact()` 一个方法里。单条太长压、整个历史太长压、不管什么场景都用同一份摘要 prompt。
- **JiuwenSwarm**:5 个独立 processor,各自独立配置、独立触发,通过 `ContextProcessorRail` 串起来按需挂载:
  - `MessageSummaryOffloader` 单条大消息 offload
  - `DialogueCompressor` 对话级压缩
  - `CurrentRoundCompressor` 当前一轮内多工具调用压缩
  - `RoundLevelCompressor` 多趟递归压缩
  - `ReasoningToolLoopCompactProcessor` 折叠重复试错循环

## 二、五件大事:Starter 没做,JiuwenSwarm 做了

### 1. 压缩了能找回来(offload + reload)

- **Starter**:把 ToolMessage 的 content 直接换成摘要,原文彻底丢。用户上传 5000 token 数据 → 压缩成摘要 → 后续问"华东区数字是多少" → 摘要里没这层 → 答"信息已压缩"。
- **JiuwenSwarm**:用 `[[OFFLOAD:...]]` 索引标记把原文外置,`enable_reload=true` 时模型按需把原文拉回上下文。**压缩可逆。**

### 2. 多趟递归压缩

- **Starter**:全局压缩一次到位,收益率<5% 就跳过。长上下文经常一次压不动,直接放弃,任由上下文撑爆窗口。
- **JiuwenSwarm**:`RoundLevelCompressor` 三趟递归,每趟目标 token 递减,前一趟的输出当后一趟的输入:

| 趟次 | 输入 | 输出目标 | 压缩比 |
|---|---|---|---|
| 第一趟 | 25 万 | 3 万 | 8:1 |
| 第二趟 | 3 万 | 2 万 | 1.5:1 |
| 第三趟 | 2 万 | 1 万 | 2:1 |

每趟压缩比都温和,模型容易产出高质量摘要。

### 3. 折叠试错循环

- **Starter**:ReAct agent 反复试错(改 bug 跑测试、调参数试配置)产生几十条相似消息,当普通历史一起摘要。失败过程和成功路径混在一起,摘要质量下降。
- **JiuwenSwarm**:`ReasoningToolLoopCompactProcessor` 识别"连续 N 轮 reasoning 内容相似 + 调用相同工具集",`consecutive_threshold=3` 触发后只保留最近 1 轮完整内容。**token 节省 50%+ 且不丢信息。** 这是唯一不调 LLM 的纯规则 processor。(算法细节见附录 A.2.5)

### 4. 当前轮次压缩

- **Starter**:单条压缩只针对"一条巨型消息"。对"一轮里调了十几个工具,合计撑爆窗口"这种场景没有专门处理,只能等触发全局压缩。
- **JiuwenSwarm**:`CurrentRoundCompressor` 专治这个,带 `min_selected_tokens_for_compression`、`summary_merge_min_blocks`、`prior_context_window_size` 等精细控制。

### 5. KV cache 联动

- **Starter**:压缩了上下文消息,但 KV cache 还挂在原 session,长会话依然占显存/内存。**上下文工程只做了"消息层",没碰"cache 层"。**
- **JiuwenSwarm**:
  - `offload_session_kv_cache`:压缩历史时把对应 KV cache 卸到外存
  - `prefetch_kvc`:上下文即将被引用时预取
  - `kv_cache_affinity_config`:同会话尽量复用同一节点,保持 cache 命中

## 三、配置灵活性

### Starter 锁死的常量(JiuwenSwarm 里都是可配置的)

| Starter 常量 | 值 | JiuwenSwarm 对应配置 |
|---|---|---|
| `MAX_MESSAGES_TO_KEEP` | 6 | `messages_to_keep` / `keep_recent_messages` |
| `PROTECT_FIRST_MESSAGES` | 3 | `keep_last_round` |
| `MAX_REPORT_SUMMARY_SEGMENTS` | 3 | `content_max_chars_for_compression=200000` |
| 无 | - | `protected_tool_names: ["read_file"]` |
| 无 | - | `enable_adaptive_compression` |
| 无 | - | `enable_precise_step` + `step_summary_max_context_messages` |
| 无 | - | `offload_writeback_enabled` |
| 无 | - | `customized_summary_prompt` |

两个最值得抄的:`protected_tool_names`(代码工具结果不压,详见第二部分 1.3 决策二)和 `keep_last_round`(完整保留最后一轮对话,Starter 按"消息条数"取会把一轮拆开)。

## 四、Prompt 工程

### Starter:一份 prompt,一个方向

固定一份 `SUMMARY_PROMPT`,要求"压缩较早对话"。结构化字段(目标/约束/已完成动作/当前状态/阻塞/关键决策/已解决问题/待处理请求/相关文件/历史剩余工作/关键上下文)。强制 `[REDACTED]` 凭证脱敏。

### JiuwenSwarm:两份 prompt,两个方向

- `PARTIAL_COMPACT_PROMPT`:保留前缀,摘要尾部("继续 session"用)。强调"work completed / context for continuing work"。
- `PARTIAL_COMPACT_UP_TO_PROMPT`:摘要前缀,保留尾部("rewind"用)。强调"current work / optional next step"。

两份 prompt 都强制 `<analysis>` + `<summary>` 双块结构,要求先分析再总结,强制列出"全部 user messages"(防止用户消息被摘要掉)。还有 `NO_TOOLS_PREAMBLE` 显式禁止压缩调用时调工具("Tool calls will be REJECTED and waste your only turn")。

**Starter 没有这层约束,理论上压缩模型可能在生成摘要时尝试调工具导致摘要失败。**

## 五、Starter 现有但 JiuwenSwarm 没有的优势

1. **摘要质量硬校验**:Starter 的 `ensureSummaryQuality`(原文≥480 字符但摘要<120 字符直接抛错)比 JiuwenSwarm 严格。
2. **凭证脱敏**:Starter 强制 `[REDACTED]` 替换 API key/密码/连接串,JiuwenSwarm 的 partial compact prompt 没这层。
3. **三段切分 + 开头结尾抽样**:Starter 对单条超长报告的"三段切分 / 开头结尾抽样降级"处理非常细。JiuwenSwarm 是按 `content_max_chars_for_compression` 截断后再摘要,粒度更粗。
4. **压缩前记忆转存**:Starter 有 `onPreCompress` 回调把原文快照转存外部记忆。JiuwenSwarm 没有"压缩前转存长期记忆"这层联动(但有 offload + reload 等价能力)。

## 六、Starter `HermesStyleCompactProcessor` 工作机制详解

> 这一节把 Starter 唯一的 context processor 拆开讲清楚,作为第三部分故障排查的代码依据。代码在 `HermesStyleCompactProcessor.java`。

它就干两件事:

1. **单条压缩**:某一条消息本身太大(默认 ≥2400 token)时,把它单独摘要后替换掉。能切段的报告切 3 段逐段摘要,切不了的取头尾各 30% 采样摘要。
2. **全局压缩**:整个历史累计太大(默认 ≥10400 token)时,把消息历史切成"开头保护 3 条 + 中间摘要 + 结尾保留 6 条"三段,中间段喂给摘要模型,产出一条摘要替换中间段。

两个关键设计:

- **原文直接替换成摘要,不可逆**。JiuwenSwarm 是把原文外置到 workspace 的 JSON 文件、用 `[[OFFLOAD:...]]` 占位符按需 reload——压缩可逆。这是 Starter 最大的硬伤之一。
- **失败即抛 `IllegalStateException`**:三段切不完、采样摘要失败、摘要质量不合格(原文 ≥480 字符但摘要 <120 字符)、没配压缩模型——四种情况都直接抛错。好消息是框架层 `SessionModelContext.addMessages` 用 try/catch 把 processor 包了起来,异常被吞掉只打 warning,不会直接终止对话;坏消息是**本次压缩被跳过**,上下文继续涨,涨到超出模型输入上限时 API 调用失败,那一刻才真正"模型不回复"。所以硬抛的因果链是**间接**的:抛错 → 框架捕获 → 压缩跳过 → 上下文膨胀 → 超窗 → API 失败。

还有个已知 bug:只要历史里出现过压缩标记 `[HERMES_STYLE_COMPACT_BOUNDARY]`,下次压缩就不再保护开头,会把上一轮的摘要也压掉,变成"摘要的摘要",信息逐轮衰减。

设计哲学是"严而简"——参数少、约束强、失败就抛。简单场景下可控可预测,长对话 + ReAct 多步 + 试错循环场景下就脆了。具体 11 条根因见第三部分。

## 八、压缩逻辑对比:压中间还是怎么压

两者**都**有"压中间"的模式,但 Starter 只有这一种,JiuwenSwarm 有 5 种,且"中间"的定义完全不同。

### Starter:按消息位置三段切,只压中间

```
[开头保护 3 条] [中间摘要段] [结尾保留 6 条]
       ↓             ↓             ↓
     不动         压成 1 条        不动
```

- "中间"= 消息列表里第 4 条到倒数第 7 条这个区间,**按位置算**
- 不管这些消息属于哪一轮、是什么角色,一锅炖成一条 summary
- 中间段被一条"摘要消息"替换,前面打 `[HERMES_STYLE_COMPACT_BOUNDARY]` 标记
- 头尾按条数切,不看轮次边界

### JiuwenSwarm:5 个 processor 5 种压缩方式

**1. MessageSummaryOffloader —— 压单条(点压缩)**

不动整段历史,只挑**那一条**过大的 ToolMessage,替换成摘要 + `[[OFFLOAD:...]]` 占位符。原文外置到 JSON 文件。

```
[..., 大消息, ...]      → [..., 摘要+占位符, ...]
       ↑                       ↑
     压这一条               其他全部不动
```

**2. DialogueCompressor —— 按轮次压中间(轮次感知)**

跟 Starter 最像,但"中间"按**轮次边界**切,不是按位置:

```
[轮1完整] [轮2完整] [轮3完整] ... [轮N-1完整] [轮N最新+尾部N条]
   ↓          ↓          ↓                  ↓
  压         压          压                 不压
```

- 识别完整 ReAct 轮(User → Assistant_final 不含 tool_calls 为一轮)
- 只压消息数 > 2 的轮(有压缩价值)
- 保留最近 N 条 + 最新一轮不压
- 每轮压成一个独立 memory block,**保留轮次结构**

**3. CurrentRoundCompressor —— 压当前轮内选中段**

不动历史,只动当前轮(用户最新一次提问起的那一轮):

```
当前轮内: [user query | 历史 memory blocks | 选中段 | 最近消息]
                                  ↑
                              只压这一段
```

- user query 不压;已有 memory blocks 不压(只当参考);最近消息(边界上下文)不压
- 选中段(当前轮里跑了几十次工具调用那部分)压成一个新 memory block **追加**到累积列表
- 阶段二:累积 memory blocks 太多时合并相邻老块

**4. RoundLevelCompressor —— 整窗口三趟渐进**

不是"压中间",是**整窗口渐进压缩**(临满前最后一道):

| 趟 | 输入 | 输出目标 | 怎么压 |
|---|---|---|---|
| 第一趟 | 所有 L0 块 | 30k | 按 ReAct 轮全压成 L1 memory block,递归合并直到达标 |
| 第二趟 | 第一趟结果 | 20k | 减少 keep_recent,扩大压缩范围 |
| 第三趟 | 第二趟结果 | 10k | keep_recent=0,全上下文都是压缩目标 |
| 兜底 | 三趟后仍超 | 硬截断 | 头尾保留策略,不是砍头 |

**5. ReasoningToolLoopCompactProcessor —— 不压,直接删**

不动中间,扫"连续 N 轮 reasoning 相似 + 工具集相同"的尾部,把 trailing 重复轮**全部删除**,只留一条合成 summary。这是删除,不是压缩。

### 对照表

| 维度 | Starter | JiuwenSwarm |
|---|---|---|
| 压缩模式数 | 1 种 | 5 种 |
| 主要策略 | 压中间(按位置) | 压单条 + 压轮次中间 + 压当前轮选中段 + 整窗口渐进 + 删重复 |
| "中间"的定义 | 消息列表第 4 到倒数第 7 条 | 完整 ReAct 轮的集合(轮次感知) |
| 是否保留轮次结构 | 不保留(一锅炖成 1 条) | 保留(每轮 1 个 memory block) |
| 头尾切法 | 按消息条数(头 3 尾 6) | 按轮次(尾部 N 条 + 最新一轮完整) |
| 整窗口兜底 | 没有,一次压不动就跳过 | RoundLevelCompressor 三趟渐进 + 硬截断兜底 |
| 单条大消息处理 | 走单条压缩(也压中间逻辑的变种) | MessageSummaryOffloader 专门处理,带 offload + reload |
| 当前轮内多工具 | 没专门处理 | CurrentRoundCompressor 段内压缩 + 累积块合并 |
| 试错循环 | 当普通历史压 | ReasoningToolLoop 直接删重复轮 |

### 一句话

**Starter 是"按位置三段切,只压中间",JiuwenSwarm 是"按场景拆五种压法,其中只有 DialogueCompressor 跟 Starter 类似也是压中间,但按轮次切不按位置切"。**

最关键差别不是"压不压中间",而是:

1. **Starter 的"中间"是位置概念,JiuwenSwarm 的是结构概念**——前者按条数切,会把一轮从中间劈开;后者按轮次切,完整轮要么整轮压要么整轮留
2. **Starter 只有一种压法应付所有场景,JiuwenSwarm 按膨胀模式分诊**——单条大消息走 offloader、整轮膨胀走 dialogue、当前轮工具链过长走 current-round、临满走 round-level、试错循环走 loop-fold。Starter 用一把锤子敲所有钉子,该用螺丝刀的地方把螺丝敲歪了
3. **Starter 没有"整窗口兜底"**——一次压不动就跳过,JiuwenSwarm 有三趟渐进 + 硬截断头尾保留,保证临满前一定能压下来

# 第二部分:JiuwenSwarm 上下文实践详解

> 聚焦客户最常遇到的三类问题:长对话后模型"忘"、会话内子任务串话、跨会话记忆。每节按"问题本质 → 方案骨架 → 关键决策 → 易抄错的点"展开。

## 现象一:跑几十轮后模型开始"忘"

### 问题本质

模型"忘"不是模型的问题,是工程策略的问题。常见三种错误做法:硬截断窗口(关键决策来龙去脉突然消失)、一刀切全摘要(细节丢失,模型读代码/查文件结果被压没)、只在最后一刻才压(关键路径上跑,要么慢要么压不充分)。根因是把"压缩"当成单一动作——"忘"有多种膨胀模式,需要不同时机、不同力度的对策。

### 方案骨架:多级渐进压缩

压缩拆成五级,按代价从低到高、按时机从频繁到罕见排列:

| 级别 | 触发条件 | 解决的膨胀模式 | 是否调 LLM |
|---|---|---|---|
| 重复轮折叠 | 连续 N 轮相同 reasoning + 工具集 | "原地踏步"型膨胀 | 否(纯规则)|
| 单消息摘要卸载 | 单条 tool 输出超阈值 | 大文件/大搜索结果吃掉窗口 | 是 |
| 对话轮聚合 | 累积 token 超阈值 | 跨多轮整体膨胀 | 是 |
| 当前轮内压缩 | 当前轮 token 超阈值 | 单轮内工具调用链过长 | 是(两段)|
| 整窗口渐进压缩 | 上下文占比达阈值 | 临满前主动收缩 | 是(三趟)|

### 关键设计决策

1. **为什么多级而非一级**:不同膨胀模式响应时机不同——重复轮每轮都检查(规则、便宜),单消息进入时检查(早处理省后续),整窗口在生成前检查(最后一道防线)。只用一级要么太频繁(贵),要么太迟(已经丢了)。

2. **保护性原文白名单**:不是所有内容都能压。代码片段、`read_file` 结果、用户首次需求陈述,一旦摘要就丢语义,列入白名单永远原文保留。按**工具名 + 内容类型**识别,不是按消息长度——长的不一定该压,短的不一定能压。JiuwenSwarm 默认保护 `read_file`,Starter 没这层。

3. **占位符 + 外部存储**:被压原文不丢,写占位符 `[[OFFLOAD: handle=...]]`,原文存到 workspace 下的 JSON 文件,用 handle 还能拉回原文(`enable_reload=true`)。这不是性能优化,是**可排查**的命门——压缩后行为异常要排查时,没有原文只能瞎猜。

4. **从规则到 LLM 渐进**:能用规则解决的先解决(重复轮折叠纯模式匹配,不调 LLM)。规则层吃掉 80% 的膨胀,LLM 只处理真正需要语义归纳的部分。

5. **主动 + 被动双入口**:被动是消息进入/窗口生成时 compressor 自己判断要不要压;主动是暴露 `compress_context` 入口,让上层在闲时或使用率达 80% 时主动跑。只在关键路径被动压会拖慢响应。

### 五个 compressor 的协作

五个 compressor 按时机分层协作:前四个(MessageSummaryOffloader、ReasoningToolLoop、DialogueCompressor、CurrentRoundCompressor)在消息进入时各自判断,谁触发谁处理,互不感知;RoundLevelCompressor 是窗口送模型前最后一道,处理前四个没压够的情况。协作原则有三条:**已压的块后续不再压**(避免"压摘要的摘要"雪崩)、**tool_call/result 边界所有 compressor 都保护**(切点不落在配对中间)、**早处理省后续**(单条大消息压了,后续 compressor 看到的就是压后的)。

### memory block 结构

被压的对话段不直接替换成 summary 文本,而是包成结构化 memory block,前面带六个元数据字段:`processor` / `type` / `scope`(溯源标签,便于调试)、`authority`(说"这是参考、不是真理")、`instruction_status`(说"不要当新用户请求或新助手承诺",防模型把摘要当新指令去执行)、`conflict_priority`(说"与新内容冲突时让位")。裸塞 summary 模型可能把摘要当新指令、当事实依据、当新承诺,行为完全错乱。

### 失败路径

每个 compressor 都有完整失败路径,"压不下来"绝不"为压而压":LLM 报错 / 输出非法 JSON / 压完比原来还大,都回退到原文不替换;单块失败不影响其他块;所有 LLM 路径都有非 LLM 兜底(头中尾截断、硬截断头尾保留等);每次失败都记录原因。**核心原则**:绝不"为压而压"、单点失败不影响整体、兜底永远存在、记录失败原因。客户最容易踩的坑就是只抄 LLM 压缩逻辑、不抄失败兜底——LLM 一报错整个 agent 就崩(对应 Starter A1/A2)。

### 易抄错的点

1. 白名单写得太宽——把"看起来长的"全压,代码细节没了。建议保守起步,只压对话类,tool 输出全保;
2. 没占位符——压完直接替换,调试时无法回溯。一定要留 handle 和外部存储;
3. 只在最后被动触发——等到 95% 才压,空间太小压不充分。建议 80% 主动触发。

## 现象二:一个会话里多个子任务串话

### 问题本质

用户在一个会话里说"帮我分析 A 文件,同时查下 B 问题",Agent 起两个 workflow 并行跑,A 的工具结果进了 B 的上下文窗口,B 看到 A 的内容回答混着来;或更隐蔽:A 跑完没清理,B 启动时继承 A 的历史消息,模型以为还在 A 语境里。根因是**单会话只持有一个 ModelContext,所有并行子任务共用同一份消息列表**,子任务之间没有隔离边界。

### 方案骨架:多 context 隔离

把"一个会话一个上下文"升级为"一个会话多个上下文,按 context_id 区分"。ContextEngine 按 `session_id + context_id` 管理多个并行 ModelContext:主对话用 session_id 当 context_id,每个 workflow 用 workflow_id 当 context_id 创建独立 context,子任务结束调 `clear_context` 释放。每个 context 有独立消息缓冲、工具状态、checkpointer,互不共享。

### 关键设计决策

1. **context_id = workflow_id**:天然映射——一个 workflow 就是一个独立任务边界,workflow_id 已有不需额外生成,失败排查时按 workflow_id 一查就知道是哪个任务的上下文。

2. **创建点单一化**:context 的创建必须统一在 Agent 的 `invoke` 入口,workflow 组件不能自己 create_context,只从 invoke 参数接收 context。散建会导致 context 数量爆炸、无法统一生命周期管理、无法做缓存优化。

3. **统一生命周期**:每个 context 走 `create → 跑 workflow → save 持久化 → clear 释放` 流程。漏 save 重启后丢失;漏 clear 内存累积(长跑服务尤其致命)。

4. **长跑服务主动清理**:不能等 GC,必须主动清——用户结束会话全清;只结束某个子对话精确清;服务停机前 save + clear 持久化后释放。

### 主对话与子任务 context 的关系

主对话 context 用 session_id;workflow context 用 workflow_id,与主对话**完全隔离**——workflow 的工具结果不进主对话窗口。workflow 结束后可选把 summary 注入主对话("我刚分析完 A,结论是..."),这是**显式跨 context 信息流**,不是隐式串话。主对话的 user 消息要在 workflow 里看到,需要显式 `add_messages` 把它加到 workflow context,不是自动共享。**隐式共享就是串话**,显式注入是可控的——主对话决定"给 workflow 看什么",跨 context 信息流必须有审计痕迹。

### 易抄错的点

1. 组件里散建 context——客户最容易犯。组件 A 自己 create 了跑完不清,跑几十次后内存爆。**强制约束:组件只能接收,不能创建**;
2. 多 context 共享消息缓冲——为"省内存"让多个 context 共用一份消息列表再各自索引,等于没隔离。每个 context 必须独立缓冲;
3. 子任务异常没清 context——异常路径也要 clear,否则下个子任务复用同一 context_id 拿到上一个的残留。

## 现象三:跨会话记忆

### 问题本质

跨会话记忆有两个极端:**不记**(用户回来发现 agent 不记得,每次从零开始,体验割裂)和**乱记**(A 用户记忆串到 B、敏感信息被记下、重复抽取浪费 token、记忆互相矛盾)。难点是"记什么、什么时候记、怎么不串味、怎么不重复"。

### 方案骨架:两条互补链路

跑两条完全独立的链路,覆盖不同时间尺度:**即时抽取(Auto Memory)** 每次会话结束触发,深度浅,覆盖近期,写到单条记忆文件 + MEMORY.md 索引;**周期整合(Dreaming)** 后台定时(默认 4h),深度深,覆盖全局,写到 DREAMING.md 整合文件。两者互补——前者快但浅,后者慢但全局。

### Auto Memory 关键设计

1. **用子 agent,不用裸 LLM 调用**:抽取起一个子 agent 完成,继承父 agent 的 model / system_prompt / tools / 消息前缀——四个全对齐是为了让**子 agent 的 prompt cache key 与父 agent 完全一致**,直接命中父刚跑过的 KV cache,抽取几乎不额外烧推理开销。裸 LLM 调用 cache key 对不上,等于从零发起一次完整推理。

2. **工具白名单 rail**:子 agent 只挂记忆类工具(write/edit/read/search),不能调代码执行、文件操作等其他工具——抽取不需要这些能力,给了反而风险。

3. **互斥检测**:抽取前先扫历史,看主 agent 是否已显式调过 `coding_memory_write`。调过就跳过,避免重复抽取和重复写入。

4. **输出格式标准化**:记忆文件统一 `frontmatter(name/description/type) + 正文`,配套 MEMORY.md 索引,让后续检索、去重、版本管理都有抓手。

### Dreaming 关键设计

1. **增量扫描 + checkpoint**:不全量扫描(贵且重复),用 checkpoint 记录每个已扫会话的 `history_mtime + round_count`,下次只看 mtime 变化的会话,支持断点续扫。

2. **忙时退避**:主流程忙时推迟 dreaming,检测到主 agent 有活跃任务本轮跳过,下个周期再试。后台任务不抢主流程资源。

3. **管线四段**:扫描新会话 → 压缩成紧凑文本 → LLM 抽取知识项 → 去重合并到整合文件。每段独立,任一段失败不影响其他段。

4. **与即时抽取写不同文件**:即时抽取单条细粒度记忆用于精确检索,周期整合全局视角用于宏观理解,两者数据不混,检索时各取各的。

### 检索:hybrid 融合

记忆索引统一在一个 SQLite 里同时持有向量表 + embedding(语义召回)和 FTS 表 + BM25(关键词召回),两路候选融合去重后按归一化分数加权(默认 0.5/0.5,可调)返回最终 top-K。**纯向量会漏关键词精确匹配**(用户名、文件名、错误码),**纯 BM25 会漏语义近似**("用户偏好 Python" vs "用户喜欢 Python 风格"),两者互补,hybrid 召回率最高。数据源不只是记忆文件——会话历史本身也当记忆源索引,一次写入多次检索。

### 合规底线

集中维护一份"禁写模式"列表(密码、API key、Secret、Token、身份证、手机号、信用卡号…),所有记忆写入前过一遍。这一步不是性能/体验优化,是**合规底线**——客户自建最容易漏,出了事就是大事(敏感信息泄漏)。

### 记忆作用域

| 作用域 | 写到 | 谁能读 |
|---|---|---|
| 用户级 | `~/.jiuwenswarm/memory/<user>/` | 该用户的所有项目 |
| 项目级 | `~/.jiuwenswarm/projects/<proj>/memory/` | 该项目的所有会话 |
| 会话级 | session checkpointer | 仅当前会话 |

默认项目级——大多数记忆是项目相关知识。用户级跨项目共享(如"用户偏好 Python"),会话级会话结束就过期。作用域要分离——全塞项目级会导致用户偏好无法跨项目复用,全塞用户级会污染其他项目。

### 易抄错的点

1. 抽取用裸 LLM 调用——每次从零起推理,token 开销大且破坏主对话 cache 命中率。建议子 agent + 继承父 cache key;
2. 没互斥检测——主 agent 已写过记忆子 agent 又抽一遍,重复写入。先扫历史看是否已写过;
3. 没禁写规则——用户在对话里贴了 API key 被记下来。**必须做,不是可选项**;
4. 检索只用向量——纯向量召回会漏关键词精确匹配。建议 hybrid(向量 + 关键词)。

## 三大现象的能力边界

| 现象 | openjiuwen 现成度 | 客户自建工作量 | 主要坑 |
|---|---|---|---|
| 一·压缩防"忘" | **高**(5 个 processor 全现成,含 memory block 包裹/收益校验/tool_call 边界保护/占位符 + 外部存储/头中尾截断兜底/ReasoningLoop bailout 计数器)| 极小(挂 Rail + 配 Config + 抄 LOOP_COMPACT bailout 机制)| 误以为要自己写算法,结果花几周复刻已有的东西 |
| 二·多子任务隔离 | **极高**(全套 API:create/get/save/clear、context_id 参数、消息缓冲隔离、checkpointer 持久化都现成)| 几乎零(只是纪律约束:入口统一 create、用 workflow_id 当 context_id、组件签名加 context 参数且禁止自己 create、跑完/异常/会话结束都 clear)| 误以为很复杂或共用单 context 导致串话;或开了多 context 忘清理,长跑服务内存爆 |
| 三·跨会话记忆 | **中**(记忆工具、禁写规则、DreamingOrchestrator 调度框架、外接记忆 provider 接口都现成;但 Orchestrator 只提供调度,业务逻辑要自己写)| 中(Auto Memory 管线 cache sharing + 互斥检测 + 工具白名单、Dreaming Sweeper 管线、MemoryIndexManager 都要抄要写)| 误以为一个开关就能开;以为 DreamingOrchestrator 就够了(它只调度,业务要自己写);跳过禁写规则就是数据泄漏事故;Auto Memory 用裸 LLM 调用而不是子 agent + cache sharing,每次抽取从零起推理且破坏主对话 cache 命中率 |

一句话:**现象一、二基本是"配置 + 纪律"就能解决,现象三是"配置 + 自己实现管线"**。客户自建 DeepAgent 时把现象一和二先做好(成本低收益大),现象三按需投入。

这三类问题背后是同一条设计哲学:**把"上下文"当成有生命周期、可派生、可清理的对象**,而不是"一串消息"。共同抓手是**显式生命周期管理**——什么时候创建、压缩、清理、抽取,每一步都要有明确触发点和清理点,不能依赖 GC 或巧合。

## 其他上下文 / 压缩 / 记忆相关实践

### 组 A:会话级状态管理

- **A1. 不完整上下文自愈**:每轮 ReAct 前扫消息列表,没配对 tool_result 的 tool_call 补占位、顺序错的重排、参数不合法的规整。挂在 rail 的 `before_invoke` 和 `on_model_exception` 钩子。**为什么**:用户 ESC、流截断、进程崩溃后从 checkpoint 恢复会留下破损上下文,下一轮 API 直接报错。
- **A2. HITL 中断与 stale state 清理**:会话重建(rewind / fork / branch)必须同时清三处:context 状态、runtime state(迭代计数 / stop_condition / pending_follow_ups)、HITL 中断状态(`INTERRUPTION_KEY` + `INTERRUPT_AUTO_CONFIRM_KEY`)。**为什么**:HITL 工具把中断状态持久化到 checkpointer,用户中断后没继续直接发新消息,旧中断还在,agent 把新消息当"对旧中断的回复"。这是"紊乱"里最隐蔽的一类——日志正常但行为完全错乱。
- **A3. rail 失败降级**:rail 加载 / 构造失败时返回 None,不阻塞主流程。**fail-closed 不是 fail-stop**,任何 rail / processor 挂了都不应让整个 agent 跑不起来。

### 组 B:会话重建与持久化

- **B1. 双轨持久化**:会话同时写两份——`history.json` 留原始流式事件(reasoning chunks / tool_call / tool_result / final / 压缩边界标记),用于审计、回放、rewind 重建;`Checkpointer (SQLite)` 留压缩后窗口 + runtime state,用于热恢复、断点续跑。后者只持滑动窗口(旧消息已压成 summary),所以**不能直接拿当前窗口 rewind**——rewind 要回到更早的轮次,那些轮的原始消息已被压没,必须从 history.json 重建。
- **B2. rewind 从原始事件重建**:"回到第 N 轮重做"标准流程:截断 history.json 到目标轮 → 流式事件状态机重建 BaseMessage(reasoning chunks 按 ID 拼接、tool_call 配对 tool_result、跳过 delta/metadata 类事件)→ 过滤孤儿 tool_call → clear 旧 context + 三处状态清理 → 补 UserMessage 保证角色交替 → create 新 context + save 持久化。
- **B3. 会话边界标记**:手动压缩时在 history.json 写三类记录:`context.compact_boundary`(标记"此处之前已被压")、`context.rewind_summary`(一句话告知模型"已总结 N 条消息")、`context.compact_summary`(实际的 LLM 摘要内容)。rewind 重建时前两类转成 UserMessage 让模型当作用户给的语境,boundary 标记本身丢弃。防"模型突然发现少了一段对话而困惑"。
- **B4. fork / branch 会话**:复制源会话目录到新 session_id,深拷贝源 runtime state,但 reset iteration=0、清 stop_condition_state、清 pending_follow_ups、生成新 plan slug。源会话不动。**fork 是"复制 + 局部 reset",不是全量继承**——分支要继承"已完成工作"上下文,但不能继承"已迭代 N 次"状态,否则一启动就触发 stop condition。
- **B5. 流式事件状态机重建**:history.json 存的是一条条流式事件,重建可送模型的消息列表时必须按状态机走——reasoning chunks 按事件 ID 拼接(顺序可能因异步写入错乱)、tool_call 按 tool_call_id 配对(不能按位置)、跳过 delta/metadata 类事件(否则控制符塞进上下文污染模型输入)、跳过压缩边界标记本身(转成 UserMessage 或丢弃)。所有"乱码、顺序不对、控制符泄漏"现象的根因 90% 在这一层没做对。
- **B6. 文件锁 + 写入队列**:history.json 和 checkpointer 的写入必须串行化——每个会话文件挂一把 `_FILE_LOCK`,同一会话写入排队到 `_WRITE_QUEUE` 依次执行,写入是原子操作。长跑服务尤其关键——多 agent 并发跑同一会话(主 + 子 + Auto Memory 抽取子 agent)会同时往 history.json 写。不加锁会出三类破损:并发覆盖(丢一段事件)、文件破损(半截 JSON parse 失败)、checkpoint 错位(窗口和事件对不上)。

### 组 C:压缩的运行时控制

- **C1. processor 锁 + 主动压缩入口**:压缩进行中加锁,新消息只入队不触发被动 processor,避免压缩与新消息竞争;同时暴露 `compress_context` 主动入口,让上层在闲时或使用率 80% 时主动跑一遍,避免在用户等待的关键路径上压缩。(对应 Starter 的 `ContextCompressionGuard` 已实现但没接线的问题,详见第三部分 C3)
- **C2. 手动压缩入口**:暴露 `compact_partial_session`,让用户/上层主动选择从某轮压缩(`from` / `up_to` 两个方向),同步裁掉 diff / file_ops 的对应尾部。比被动压缩更可控——用户能精确选哪段压。

### 组 D:性能与资源控制

- **D1. KV cache 亲和(可选)**:窗口重建时算 `ContextWindowChange` 差异,团队级生命周期事件发 `offload` / `prefetch` 信号给推理引擎,按区间失效 / 预取 KV cache。**需要推理后端支持**——开源部署无此能力时不影响功能,默认关。
- **D2. 忙时退避 + fire-and-forget**:后台任务(Auto Memory 抽取、Dreaming 整合)感知主流程负载,主 agent 忙时推迟;会话结束时立即 fire-and-forget 起抽取任务不等完成就返回响应。后台任务不抢主流程资源。
- **D3. 增量扫描 + checkpoint**:Dreaming Sweeper 不全量扫描,用 checkpoint 记录 `history_mtime + round_count`,下次只看 mtime 变化的会话,把扫描成本从 O(总会话数) 降到 O(变更会话数)。

### 优先级分级

- **P0 必做**(不做会出问题):不完整上下文自愈、HITL 中断清理、rail 失败降级、保护性原文白名单;
- **P1 建议做**(不做会偶发问题):双轨持久化、processor 锁 + 主动压缩、忙时退避 + fire-and-forget、增量扫描 + checkpoint;
- **按需做**(有需求才做):rewind 重建、会话边界标记、fork/branch、手动压缩入口、KV cache 亲和。

起步阶段建议只做 P0 + P1,按需做按需项。不要一上来全套抄——很多功能(如 KV cache 亲和、fork/branch)客户自建场景根本用不到。

## 附录:五个 compressor 的算法要点

所有 compressor 走同一条流水线:trigger 判断要不要压 → 选压缩目标(切成"要压的段" + "保留的尾部")→ 调 LLM(或纯规则)生成 summary → 用 memory block 包裹 summary 替换原段 → 校验压缩收益(压完要比原来小才接受,否则回退)→ 失败兜底(LLM 报错/输出非法/超 token → 截断或保留原文)。memory block 包裹、压缩收益校验、保护性 tool_call 边界都贯穿所有 compressor,下面各 compressor 只讲差异。

- **MessageSummaryOffloader**:扫历史找到触发这条 tool 消息的 function_call,推断"当前任务步"(简单模式取最后一条 user 消息,精确模式可选再调一次 LLM 抽任务描述),用"任务步 + 工具调用 + 工具输出"构造压缩 prompt,让 LLM 输出结构化 JSON:`summary`(摘要本体) + `offload_data_explanation`(分类/描述/可推断性)。摘要拼上 `[offloaded_info]` 元数据头替换原内容,原始 tool 内容写到外部存储留 handle。失败兜底走"头-中-尾三段智能截断"(前 33% + 中 33% + 后 33%),比一刀切尾巴好——工具输出关键信息往往分散在头(参数)、中(结构)、尾(结果)。

- **DialogueCompressor**:识别对话轮(UserMessage → AssistantMessage 不含 tool_calls 的最终回复为一对,轮内所有 reasoning + tool_call + tool_result 都属这一轮),只压消息数 > 2 的轮,保留最近 N 条 + 最新一轮不压。把要压的轮编号成 `react_1 / react_2 / ...`,连同"压缩目标前后的上下文"一起塞给 LLM,**多块并发**一次压多轮(不是一轮一次),prompt 里有信息优先级表(任务目标 > 关键事实依据 > 未完成工作 > 交接状态 > 决策与变更 > 重要文件/产物 > 支撑细节)。每轮 summary 包成 memory block 替换原段,单块失败不影响其他块。

- **CurrentRoundCompressor**:最复杂,分两阶段。**阶段一**:找当前轮边界(从最新 user 消息到最近完成轮末尾),把上下文切成四段——用户查询、历史累积 memory block(不压,只当参考)、选中消息段(要压,唯一目标)、最近消息段(边界上下文,不压);prompt 严格约束"只压 selected,不能改写 prior memory blocks,不能吸收 recent 内容",防 LLM 自作主张把所有老摘要重写一遍;输出包成 memory block **追加**到累积列表(不是替换历史块)。**阶段二**(条件触发):累积 memory block 总 token 超 `accumulated_summary_token_limit`(默认 20000)且块数 ≥ `summary_merge_min_blocks`(默认 3)时,把连续多个老块划成合并组,调一次 LLM 合并成一个新的更短块。

- **RoundLevelCompressor**:三趟渐进。**第一趟**(L0 → L1):按完整 ReAct 轮切分,跳过已是 memory block 的块(避免重复压),保护 tool_call 边界,把所有 L0 块送 LLM 压成 L1 memory block,目标 token = 30k;如仍超窗口,把已压的 L1 块作为新输入继续合并相邻块,直到窗口达标或无法再合并。**第二趟**(激进保尾):第一趟后仍超窗口,减少保留尾部消息数(`keep_recent` 调小),扩大压缩范围,目标 token = 20k。**第三趟**(全上下文):第二趟后仍超窗口,`keep_recent=0`——不保留任何最近消息,全上下文都是压缩目标,目标 token = 10k,这是最狠的一趟。**兜底**:三趟后仍超窗口直接硬截断,截断时用头尾保留策略,不是简单砍头。

- **ReasoningToolLoopCompactProcessor**:**唯一不调 LLM 的 compressor**。模型陷入"思考 → 调同一组工具 → 类似结果 → 又思考 → 又调同一组工具"循环时,扫描消息每个 AssistantMessage(有 tool_calls + reasoning)启动一个 round,向后扫匹配 ToolMessage 配齐所有 tool_call_id;算指纹 = `(整理后的 reasoning 文本, 排序后的工具名列表)`;从最新 round 往前扫找连续指纹相同的 trailing rounds;连续相同数 ≥ `consecutive_threshold`(默认 3)才触发,把所有 trailing 相同轮**全部删除**,只保留一条合成 summary 消息——内容是"最新一轮的 tool_call + tool_result 的结构化 JSON" + 一段警告文本"检测到连续 N 轮相同 reasoning + 工具集,已折叠较早重复轮"。每次折叠都给 session 状态里的 `LOOP_COMPACT_BAILOUT_STATE_KEY` +1,达到阈值后 rail 层抛 `AbortError` 终止整个 invoke(防无限循环)。

# 第三部分:Starter 多轮对话后不回复/回复异常排查

## 一、背景

用户反馈:在使用 starter 进行多轮对话后,出现两种异常:

1. 模型不再回复
2. 回复内容不符合预期

下面基于当前 starter(`HermesStyleCompactProcessor` + `ContextCompressionGuard`)的代码梳理可能根因,并给出按优先级排序的修复建议。

## 二、可能根因(按发生概率/严重性)

### A. 硬终止类 —— 间接导致"不再回复"

> **重要前提**:框架层 `SessionModelContext.addMessages`(line 122-136)用 try/catch 把每个 processor 的 `onAddMessages` 整个包起来。下面 A1-A4 抛的 `IllegalStateException` 都会被 catch、log warning、**吞掉**,不会直接终止对话,用户消息照常进 buffer,模型照常被调。
>
> 真实链路是**间接**的:抛错 → 框架捕获 → **本次压缩被跳过** → 上下文持续膨胀 → 最终超出模型输入上限 → API 调用失败 → 那一刻才"模型不回复"。所以 A 类的严重性不在"立刻终止",而在"压缩彻底失效,上下文必然撑爆窗口"。

#### A1. 摘要质量校验抛错

`ensureSummaryQuality` 在原文≥480 字符但生成摘要<120 字符时直接抛 `IllegalStateException("历史上下文摘要质量不合格")`。

- 多轮后历史长度必然超 480 字符,只要摘要模型一次输出不稳定(容量不够、prompt 过长、温度问题)就抛错。
- 抛错被框架吞掉,本次压缩跳过,上下文原样保留继续涨。
- **这是最可能的元凶**——单次抛错不致命,但每次都跳过=压缩形同虚设,长对话必然撑爆窗口。

涉及代码:`HermesStyleCompactProcessor.ensureSummaryQuality` / `generateSummary`。

#### A2. 摘要模型调用失败抛错

`generateRequiredSummary` 在模型返回空或抛错时 `IllegalStateException("超长消息摘要失败,已停止继续上下文处理")`。

- 网络抖动、限流、超时(默认 120s)都会触发。
- 同样被框架吞掉只打 warning,本次压缩跳过,上下文继续涨。

涉及代码:`HermesStyleCompactProcessor.invokeSummaryModel` / `generateRequiredSummary`。

#### A3. 三段切分失败抛错

`splitIntoReportSegments` 在三段都装不下时抛 `IllegalStateException("超长报告无法在三段安全预算内切分")`。

- 某条工具输出极长(dump 大表、长日志)触发。
- 已有 `summarizeOversizedReportSample` 开头结尾抽样降级,但 `splitIntoReportSegments` 在它之前先抛错,降级路径走不到。
- 抛错被框架吞掉,这条超大消息原样留在上下文,直接吃掉窗口预算。

涉及代码:`HermesStyleCompactProcessor.splitIntoReportSegments`。

#### A4. 摘要模型没配

`invokeSummaryModel` 在 `model == null` 时抛 `IllegalStateException("未配置上下文压缩模型")`。

- `compressionModelClient` / `compressionModelRequest` 任一字段缺失(`api_key` / `api_base` / `client_provider`),`Model` 对象构造为 null。
- 第一次压缩就抛错,被框架吞掉后**每次**压缩都抛错,等于压缩功能彻底没开,上下文必然撑爆窗口。

涉及代码:`DeepAgentContextProcessorResolver.compressionModelClient` / `compressionModelRequest`。

### B. 上下文断裂类 —— 导致"回复不符合预期"

#### B1. 轮次被拆开保留

`selectTail` 按"消息条数 + token 软上限"取,没有"轮次"概念。

- **对最新一轮有保护**:`latestIndex("user")` / `latestIndex("assistant")` / `adjustForToolPair` 三道约束保证最新 user、最新 assistant、tool_call↔tool_result 配对都在 tail,最新一轮三元组不会断。
- **对较早轮会断**:compact 末尾的 `canDropFirstTailMessage` 循环会在 tail 里有多个 user 时砍掉较早的 user(`users <= 1` 这条只在"唯一 user"时保护),把它的 (assistant_tool_calls, tool_result) 留在 tail,形成"无 user 的工具调用"残段。
- 模型看到的是"突然以助手调工具开始的对话",上下文连贯性受损,回答偏离用户真实意图。

涉及代码:`HermesStyleCompactProcessor.selectTail`。对应 JiuwenSwarm 的 `keep_last_round` 设计(见第二部分 1.2 方案骨架)。

#### B2. "摘要的摘要"问题

首次压缩写入 `[HERMES_STYLE_COMPACT_BOUNDARY]`,下次 `protectedHeadSize` 检测到标记后返回 0。

- 上一轮摘要不再受头部保护,会被二次摘要。
- 多轮压缩后信息逐级失真,模型基于失真摘要回答。
- 这是**最隐蔽**的问题,多轮后必然触发。

涉及代码:`HermesStyleCompactProcessor.protectedHeadSize` 与 `compact` 的联动。JiuwenSwarm 用 memory block 元数据头 + 已压块不再压的规则规避这类问题(见第二部分 1.4 协作原则、1.5 memory block 结构)。

#### B3. 摘要被当指令

摘要里"历史任务快照"字段逐字保留最近未完成用户输入。

- 如果模型没正确识别边界声明,可能把摘要里的旧任务当新指令重新执行。
- 表现为"回复了用户没问的内容"。

涉及代码:`HermesStyleCompactProcessor.buildReplacement` 的边界声明写法。JiuwenSwarm 用 memory block 的 `instruction_status` 字段显式告诉模型"不要当新用户请求"(见第二部分 1.5)。

#### B4. read_file 类结果被压缩

没有 `protected_tool_names`,所有 ToolMessage 一视同仁。

- 代码文件内容被摘要掉,后续模型无法 refer 具体函数实现。
- 在代码类 agent 场景下回答变泛。

涉及代码:`HermesStyleCompactProcessor.isOversizedCompressibleMessage`。JiuwenSwarm 默认保护 `read_file`(见第二部分 1.3 决策二)。

### C. 压缩失效类 —— 间接放大 A 和 B

#### C1. 收益率<5%跳过

长上下文一次压缩常达不到 5% 收益率,压缩跳过,上下文持续增长直到撑爆窗口。

**"收益率"= `(压缩前token - 压缩后token) / 压缩前token`**。压一次只省 3%,不值当,跳过。跳过本身没错(单次压缩的合理性检查),错在跳过后没有降级路径,陷入"涨 → 触发 → 压不动 → 跳过 → 继续涨"死循环。JiuwenSwarm 的三趟递归就是解药——一次压不动就分三趟压,总能压到目标(见第二部分 A.4 RoundLevelCompressor)。

涉及代码:`HermesStyleCompactProcessor.compact` 末尾的收益率检查。

#### C2. 可压缩区间不足跳过

消息数 < 8(头部 3 + 尾部 3 + 待摘要 2)不压缩。

- ReAct 多步推理一轮就可能 8 条,刚触发又跳过。
- 陷入"压不动 → 涨 → 更压不动"循环。

涉及代码:`HermesStyleCompactProcessor.hasCompressibleWindow`。

#### C3. `ContextCompressionGuard` 没接入主链路

85% hygiene 阈值的主动压缩目前**没有任何调用方**。

- 压缩完全靠 65% 被动触发,可能太晚。
- 已实现但没接线的能力。JiuwenSwarm 的对应做法是暴露 `compress_context` 主动入口让上层在 80% 时主动跑(见第二部分 1.3 决策五、组 C C1)。

涉及代码:`ContextCompressionGuard.compressIfNeeded`。

### D. 配置/连接类

#### D1. 压缩模型复用主对话模型

`compressionModelRequest` 用 `temperature=0.1`。

- 主模型容量小(7B/13B)时,长历史摘要容易输出空或过短。
- 直接触发 A1。

涉及代码:`DeepAgentContextProcessorResolver.compressionModelRequest`。

#### D2. `maxContextMessageNum=5000` 兜底

到硬上限框架如何处理未知,可能直接拒绝新消息。

涉及代码:`DeepAgentContextProcessorResolver.configureForInstance`。

## 三、优先处理建议

### P0 —— 必须立即修(都是"硬抛错 → 压缩失效 → 上下文撑爆 → 不回复"链路)

#### P0-1. 把硬抛错改成"降级保留原文 + 记 warn"

**这是最致命的设计缺陷**:摘要失败应该让原文继续留在 context 里,而不是抛错让压缩彻底失效。虽然框架层会吞掉异常不直接终止对话,但每次抛错=每次压缩被跳过=上下文必然撑爆窗口,最终结果一样是"不回复"。

涉及三处:

1. `ensureSummaryQuality`:质量不达标 → 返回原文不压缩,记 warn。
2. `generateRequiredSummary`:模型失败 → 抛错往上传播时,`compactOversizedMessages` 和 `compact` 捕获后保留原文。
3. `splitIntoReportSegments`:三段装不下 → 退化到开头结尾抽样(已有 `summarizeOversizedReportSample`),不要抛错。

这正是 JiuwenSwarm 失败路径全景的核心原则:"绝不'为压而压',压不下来就回退,宁可保留原文让上层处理"(见第二部分 1.6)。

#### P0-2. 接入 `ContextCompressionGuard` 到 `DeepAgentClient.invoke` / `stream` 入口

在每次调用前 `compressIfNeeded(agent, conversationId, modelName, contextWindowTokens)`,让 85% 主动压缩生效。

- 这是已经写好但没接线的能力,接入成本极低。
- 解决 C3"压缩触发太晚"。

#### P0-3. 摘要模型独立配置 + retry

- 不要强制复用主对话模型
- 加一次重试
- 失败时降级保留原文(对应 P0-1)

涉及代码:`DeepAgentContextProcessorResolver.compressionModelRequest` / `compressionModelClient`。

### P1 —— 修上下文断裂(导致"回复不符合预期")

#### P1-1. 修"摘要的摘要"问题

`selectTail` 和 `protectedHeadSize` 联动 bug。

两种方案:

- 让带 `MESSAGE_SUMMARY_METADATA_KEY` 标记的摘要消息也进头部保护,或
- 在 `compact` 时显式跳过已压缩消息不参与二次摘要

涉及代码:`HermesStyleCompactProcessor.protectedHeadSize` / `selectTail` / `compact`。JiuwenSwarm 用"已压的块后续 compressor 不再压"规则规避(见第二部分 1.4 协作原则)。

#### P1-2. 引入"轮次"概念到尾部选择

对应 JiuwenSwarm 的 `keep_last_round`。

- 在 `selectTail` 里识别"最近一个 user 消息到下一个非 tool 消息"作为完整一轮
- 保证最近一轮 user-assistant 不被拆开

涉及代码:`HermesStyleCompactProcessor.selectTail`。

#### P1-3. 加 `protected_tool_names` 配置

给 ToolMessage 加白名单(默认 `read_file` 等)。

- 白名单内的工具结果不压缩
- 只保留 token 软上限内的原文

涉及代码:`HermesStyleCompactProcessor.isOversizedCompressibleMessage` / `HermesStyleCompactProcessorConfig`。这是 JiuwenSwarm 默认就有的配置项(见第二部分 1.3 决策二)。

### P2 —— 结构性改进(借 JiuwenSwarm)

#### P2-1. 拆分处理器

把 `HermesStyleCompactProcessor` 拆成:

- `MessageSummaryOffloader`(单条压缩,对应 A.1)
- `DialogueCompressor`(全局压缩,对应 A.2)
- `ReasoningToolLoopCompactProcessor`(循环折叠,对应 A.5)

理由:当前 `compact()` 逻辑高度耦合,改任一处都要动整个文件,且单条压缩和全局压缩共用一份摘要 prompt 不合理。

#### P2-2. 加循环折叠

ReAct 试错循环(改 bug 反复跑测试)场景非常多。

- 识别"连续相同 reasoning + 工具集"折叠成 1 轮
- token 节省 50%+ 且不丢信息

#### P2-3. 多趟递归压缩

把全局压缩改成 first/second/third pass 递归。解决 C1 长上下文"一次压不动就放弃"。

### P3 —— 长期演进

#### P3-1. offload + reload

- `[[OFFLOAD:...]]` 索引标记
- 启用框架 `enable_reload`
- 解决压缩不可逆

#### P3-2. KV cache 联动

- 把上下文工程延伸到推理引擎层
- 压缩时 offload/prefetch KV cache

## 四、排查顺序

实战上建议按这个顺序定位:

1. **看日志**:搜以下关键字,能直接区分是 A 类(硬抛错)还是 C 类(跳过)
   - `IllegalStateException`
   - `历史上下文摘要质量不合格`
   - `超长消息摘要失败`
   - `未配置上下文压缩模型`
   - `Hermes-style compression skipped as ineffective`
   - `超长报告无法在三段安全预算内切分`

2. **看压缩模型配置**:确认 `context-compression` 段的 `model`、`backend.api_key`、`backend.api_base`、`backend.client_provider` 都齐全,`Model` 对象不为 null。

3. **看会话消息数和 token**:走到第几轮、消息条数、估算 token。如果走到几千条还没压缩,大概率是 C 类失效。

4. **看摘要内容**:从持久化的消息列表里找 `[HERMES_STYLE_COMPACT_BOUNDARY]` 标记
   - 看摘要是否合理
   - 是否出现"摘要的摘要"(多次出现的摘要里包含上一轮摘要的字段)

5. **看尾部保留是否拆开轮次**:检查最近保留的几条消息是否成对
   - 有 ToolMessage 必有对应的带 toolCalls 的 AssistantMessage
   - 最近一轮 user-assistant 是否完整保留

## 五、总结

**P0 三件事(改硬抛错为降级、接入预留的 Guard、摘要模型独立 + retry)是最可能的元凶,也是最便宜的修复;做完再看具体哪类问题残留,对症下 P1。**

当前 starter 把"摘要失败"当成"对话失败"是设计层面的根本问题——摘要失败应该让对话继续走原文,而不是终止。
