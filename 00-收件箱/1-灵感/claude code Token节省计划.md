## 一、Token 消耗模型

Claude Code 每轮对话发送给 API 的内容 = **系统提示** + **对话历史** + **工具调用结果** + **模型输出**。

```
┌─────────────────────────────────────────────────┐
│ 系统提示 (CLAUDE.md、MCP、Skills、工具定义)      │ ← 固定，每个会话计费一次（有缓存）
├─────────────────────────────────────────────────┤
│ 对话历史 (所有之前的问答 + 工具调用)              │ ← O(n) 增长，是最大变量
├─────────────────────────────────────────────────┤
│ 工具调用结果 (Read/Grep/Bash 的输出)             │ ← 每次调用叠加，可优化空间大
├─────────────────────────────────────────────────┤
│ 模型输出 (Claude 的回复)                         │ ← 产出物，不能省但可以精简
└─────────────────────────────────────────────────┘
```

四部分成本结构完全不同，需要分别分析。

## 二、策略一：会话生命周期管理

> **攻击目标**：对话历史（token 占比最大的一项）

### 机制

- 一个 N 轮对话，第 N 轮会发送前 N-1 轮的全部内容
- 总 token 消耗与 N² 正相关（每轮都在为之前所有轮次付费）
- 虽然 Anthropic 的 prompt cache 会把历史读成本降到 10%，但 cache 写（新增内容）依然是 125%

### 量化

| 会话长度 | 平均每轮携带的历史轮次 | 历史 token 相对占比 |
|---------|---------------------|-------------------|
| 5 轮 | ~2.5 轮 | 低 |
| 20 轮 | ~10 轮 | 中 |
| 50 轮 | ~25 轮 | 高，通常已超 cache 窗口 |

**结论**：把 50 轮的长会话拆成 10 个 5 轮的短会话，历史 token 大约能省 **70-80%**。

### 具体做法

- 一个会话 = 一个任务，做完立刻 `/clear` 或开新会话
- 不要在一个会话里来回切不同主题
- 不要在对话里闲聊、反复确认

## 三、策略二：模型分层路由

> **攻击目标**：每 token 的单价

### 机制

不同模型定价差异巨大（近似比例）：

| 模型 | 相对价格 | 适合场景 |
|------|---------|---------|
| Opus 4.8 | $$$$$ 基准 | 多文件重构、架构设计、复杂调试 |
| Sonnet 4.6 | $$ (~1/3) | 日常编码、CRUD、写测试、代码审查 |
| Haiku 4.5 | $ (~1/10) | 只读搜索、信息汇总、格式化、批量操作 |

### 量化

假设你的任务分布是 20% 复杂 / 50% 中等 / 30% 简单：

| 策略 | Opus 占比 | 月成本（相对） |
|------|----------|--------------|
| 全用 Opus | 100% | 100% |
| 手动分层 | 20% | ~20%×100 + 50%×33 + 30%×10 ≈ **40%** |

### 模型选择决策树

```
你的任务是什么？
├── 只读（搜索、理解、汇总）→ Haiku 4.5
├── 写代码（增删改、测试、CRUD）→ Sonnet 4.6（默认）
└── 复杂任务（架构设计、多文件重构、疑难调试）→ Opus 4.8
```

**当前状态**：Sonnet 4.6 已设为默认模型 ✅。用 `/model` 随时切换。

## 四、策略三：CodeGraph 替代 grep/Read 循环

> **攻击目标**：工具调用结果（每次 grep + Read 叠加进上下文的源码量）

### 机制对比

```
传统方式（无 CodeGraph）：
  grep 搜索 → 列出 15 个文件
  → Read 文件 1（300 行）→ 发现不相关
  → Read 文件 2（250 行）→ 找到部分
  → Read 文件 3（200 行）→ 补全
  总计：3-5 次工具调用，750+ 行源码进入上下文

CodeGraph 方式：
  codegraph_explore("这个功能怎么实现的")
  → 1 次调用，返回 3 个关键符号 + 调用链 + 精确行号上下文（~80 行）
  总计：1 次工具调用，80 行源码
```

### 量化

单次代码探索操作，CodeGraph 比传统方式节省 **70-90%** 的工具输出 token。考虑到代码探索占一次编码任务 30-50% 的轮次，总体节省 **20-40%**。

### 当前状态

- CLAUDE.md 已配置 CodeGraph 优先规则 ✅
- 规则已修正为正确的工具名 `codegraph_explore` ✅
- 关键：AI 是否每次都遵守 — 指令清晰、优先级明确时遵守率很高

### 使用要点

1. 提问精准化：直接点名文件/符号/功能
2. 需要全文时才 `Read`：explore 返回的源码已标记为"已 Read"
3. 用 `maxFiles` 参数控制返回文件数（默认 12，单一目标可降到 4）
4. 收益边界：< 10 个文件的小项目优势不明显，> 50 个文件时显著

## 五、策略四：缓存窗口利用

> **攻击目标**：避免 cache 失效导致的历史重传

### 机制

- Anthropic prompt cache TTL = **5 分钟**
- 缓存命中时，历史读成本 = 基准价的 **10%**
- 缓存未命中时，历史读成本 = 基准价的 **100%**
- 差距是 **10 倍**

### 量化

| 节奏 | Cache 命中率 | 历史 token 成本 |
|------|------------|----------------|
| 连续提问，间隔 < 3 分钟 | ~90% | 低 |
| 断断续续，间隔 > 5 分钟 | ~20% | 高（~5x） |

**结论**：同一任务集中在一个时段连续做，不要中断。**短 + 连续 = 最优**。

## 六、策略五：Skills 压缩多轮交互

> **攻击目标**：完成任务所需的总轮次数

### 机制

Skills（brainstorming、test-driven-development、systematic-debugging 等）本质上是把"本需要 5 轮对话才能对齐的需求"压缩进一个结构化的流程里，减少了试错和来回确认。

### 量化（以 debugging 为例）

```
无 skill：
  发现 bug → 描述现象（1轮）→ AI 猜测原因（1轮）→ 你确认（1轮）
  → AI 改代码（1轮）→ 你测试后说还有问题（1轮）→ AI 再改（1轮）
  6 轮起步

有 skill：
  发现 bug → 调 systematic-debugging
  （1轮，skill 引导 AI 系统性地收集信息、假设、验证、修复）
  2-3 轮
```

**节省**：30-50% 的轮次数。

### 当前已有 Skills

- brainstorming（创意工作前必须用）
- test-driven-development（实现功能前先写测试）
- systematic-debugging（遇到 bug 时用）
- dispatching-parallel-agents（独立任务并行化）
- verification-before-completion（声称完成前验证）
- requesting-code-review / receiving-code-review

## 七、策略六：工具选择优化

> **攻击目标**：工具调用结果的冗余内容

| 场景 | 低效做法 | 高效做法 | 节省 |
|------|---------|---------|------|
| 找文件 | `find / ls -R` in Bash | `Glob` 工具 | ~50% 输出量 |
| 搜索内容 | `grep -r` in Bash | `Grep` 工具 | ~30% 输出量 |
| 读大文件 | `Read` 整个文件 | `Read` + offset/limit 只读需要的部分 | ~60-80% |
| 读已知文件 | 重复 Read 同一文件 | 信任上下文中的已有内容 | 100% |

这一项看起来琐碎，但**累积效果显著** — 假设每个工具调用平均浪费 200 tokens，一天 100 次调用就是 20000 tokens，一个月就是 60 万。

## 八、组合效果汇总

```
                   节省幅度      作用环节        实施难度
─────────────────────────────────────────────────────
① 短会话          70-80%      对话历史        低（习惯改变）
② 模型分层        60%         单价            低（已做一半）
③ CodeGraph       20-40%      工具调用结果     低（已配置）
④ Cache 利用      5x 差距      对话历史        低（连续工作）
⑤ Skills 压缩     30-50%      总轮次          低（已有 skills）
⑥ 工具选择优化    10-30%      工具调用结果     低（AI 自动）
```

**组合拳的叠加效果**（不是简单相加，因为有重叠）：

- 如果你现在月消耗是 **100 单位**：
  - 做完 ① → 大概降到 60-70
  - 做完 ①+② → 大概降到 25-35
  - 全部六项 → 大概降到 **15-25**
