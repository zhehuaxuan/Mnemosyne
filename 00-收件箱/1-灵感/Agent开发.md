# Agent 开发方法论（2026 高阶实践）

> 来源：Anthropic 官方《Building Effective Agents》与《Building agents with the Claude Agent SDK》，结合实践整理。
> 核心立场：成功的 agent 系统是**简单、可组合的模式**，不是越复杂越好。

---

## 0. 认知前提：先分清 Workflow 还是 Agent

大部分你以为需要 Agent 的场景，其实一个固定工作流（Workflow）就够了。

| | Workflow | Agent |
|---|---|---|
| 本质 | LLM 走**预定义代码路径**，人类编排每一步 | LLM **自己决定**流程和工具调用 |
| 特性 | 可预测、一致、便宜 | 灵活，但更慢更贵，错误会累积 |
| 适用 | 任务边界清晰 | 开放式问题，步数无法预先硬编码 |

> 不是"越智能越好"。Agent 用延迟和成本换任务表现，很多场景优化一次 LLM 调用就够了。**从最简单开始，不够再加复杂度**——这是官方反复强调的第一原则。

---

## 1. 核心循环（Agent 的骨架）

不管用什么框架，Agent 本质就是一个循环：

```
收集上下文 (Gather context) → 采取行动 (Take action) → 验证 (Verify) → 重复
```

很多人的 Agent 只有前两步（给工具 + 跑循环），**把第三步"验证"砍掉了**，这是新手和高手的分水岭。

---

## 2. 三个决定成败的高阶设计点

### ① ACI（Agent-Computer Interface）—— 工具设计的投入不亚于提示词

官方原话：优化工具的时间比优化提示词还多。工具是模型"最先考虑的动作"，要像给初级开发者写优秀 docstring 一样打磨：

- 每个工具写清楚：用途、参数示例、边界情况、与其他工具的边界
- **Poka-yoke（防错）设计**：改参数让错误更难发生。经典案例——SWE-bench 的 agent 用相对路径老出错，改成**绝对路径**后表现完美
- 格式选择要迁就模型：避免 diff（需要预知行数）、避免复杂 JSON；给模型足够的 token 去思考

### ② 验证机制 —— 优先级：规则 > 视觉 > LLM 裁判

- **规则（最佳）**：给输出定义明确规则并反馈哪些失败。例：lint 就是绝佳的规则反馈——生成 TypeScript 再 lint，比生成纯 JS 多好几层纠错机会
- **视觉**：UI/绘图类任务，截图或渲染图回灌给模型迭代
- **LLM 裁判**：官方明确说这是"not a very robust method"（不稳健）且有延迟，只在收益值成本时用

### ③ 上下文管理 —— 子代理是核心武器

- **子代理（Subagents）**：两大价值——①并行化；②**独立上下文窗口**，只把相关结果返回给编排器。适合"在大量信息里筛少量有用内容"的场景
- **Compaction**：上下文快满时自动压缩，防止 agent 中途失忆
- **语义搜索 vs Agentic 搜索**：先试 agentic（让模型自己 grep/tail），它更准、可维护、透明；语义搜索更快但更难维护，按需再上

---

## 3. 一个被低估的招式：把"写代码"当作 agent 的行动方式

代码是精确、可组合、无限复用的输出形态。复杂操作（生成 Excel、PPT、做数据处理）用**让 agent 写 Python 脚本执行**，比手撸工具强得多。要思考：这个任务适合用代码表达吗？

---

## 4. 五种 Workflow 模式（在需要时组合使用）

### 1. Prompt Chaining（提示链）
- 任务分解为步骤序列，每次 LLM 调用处理上一次输出，中间可加程序化检查（gate）
- 适用：任务能清晰分解为固定子任务；用延迟换准确性。例：大纲 → 校验 → 全文

### 2. Routing（路由）
- 对输入分类并导向专门化的后续任务
- 适用：存在可准确分类的类别。例：简单问题路由到小模型，难题路由到强模型

### 3. Parallelization（并行化）
- **Sectioning（分段）**：拆成独立子任务并行执行
- **Voting（投票）**：同一任务多次运行取多样输出。例：多提示词独立审查代码漏洞

### 4. Orchestrator-Workers（编排者-工人）
- 中央 LLM 动态拆解任务、委派给工人 LLM，再综合结果
- 与并行化的关键区别在**灵活性**：子任务由编排者按输入决定，非预定义。例：多文件修改的编码产品

### 5. Evaluator-Optimizer（评估者-优化者）
- 一个 LLM 生成响应，另一个在循环中提供评估和反馈
- 适用：有清晰评估标准且迭代改进有可衡量价值。例：文学翻译、多轮检索任务

## 5. Agent 的特征与使用场景

**运作方式**：以人类命令开始 → 明确任务后独立规划与操作 → 从环境获取 ground truth（工具结果、代码执行）评估进展 → 检查点/遇阻时暂停征求反馈 → 任务完成终止（常设最大迭代数保持控制）

**本质**：just LLMs using tools based on environmental feedback in a loop。实现通常很简单，因此**工具集的设计与文档至关重要**。

**适用**：开放式问题，无法预测步数、无法硬编码路径；对模型决策有足够信任度。

**风险**：成本更高、错误可能累积；建议在沙箱环境广泛测试并设护栏。

**最有价值的两个领域**：
- 客户支持：对话 + 外部信息与操作，可用"用户确认的解决方案"衡量成功
- 编码 Agent：测试可验证输出，反馈可迭代；人类审查仍不可替代

---

## 6. 选型建议（2026 现状）

- **Anthropic Agent SDK / Claude Code**：生态最成熟，内置规划、子代理、验证、compaction，几乎不用手写循环
- **LangGraph / OpenAI Agents SDK**：需要精细控制图流程、多步编排时选
- **MCP（Model Context Protocol）**：接外部系统（Slack/GitHub/数据库）的标准协议，自动处理认证，别自己写集成代码
- 框架的缺点：抽象层会**遮蔽底层提示词和响应**，增加调试难度；即使用框架也必须理解底层代码

---

## 7. 落地路径（结合自建 eval 系统）

1. **先用单次 LLM 调用 + 检索做 MVP**，别直接上 agent
2. 确认确实需要动态流程后，**手写最简循环**（配好工具集），用框架前先搞懂底层
3. **评测驱动迭代**——建代表性测试集，跑失败用例时问四连：
   - 模型误解任务了吗？（是否缺关键信息？搜索 API 结构能否优化？）
   - 反复失败？（能否在工具调用中加正式规则识别和修复？）
   - 无法修复错误？（能否给更有用/更有创造力的工具？）
   - 性能随功能增加而波动？（加测试集做程序化评估）
4. 上线前设护栏：最大步数、沙箱、敏感操作确认、token budget

---

## 8. 三条核心原则

1. **保持简单** — Maintain simplicity in your agent's design
2. **优先透明** — 显式展示 agent 的规划步骤
3. **精心设计 ACI** — 通过彻底的工具文档和测试打磨 agent-computer interface

> 一句话总结：可靠的 Agent = 简单的循环 + 精心设计的工具（ACI）+ 扎实的验证层 + 持续用 evals 迭代。不是构建最复杂的系统，而是构建**适合需求**的系统。
